# 슬라임 키우기

때려서 젤리를 모으고, 먹여서 레벨을 올리고, 레벨이 오르면 젤리가 더 빨리 모이는 방치형(idle) 게임.
의존성 없는 단일 HTML 파일이라 `index.html`을 브라우저로 열면 바로 실행된다.

## 실행

`index.html`을 더블클릭한다. 끝.

저장이 안 된다는 메시지가 뜨면(브라우저가 `file://`에서 localStorage를 막는 경우) 이 폴더에서 로컬 서버를 띄우고 `localhost:8000`으로 접속한다.

```
python -m http.server
```

## 담고 있는 것

방치형 장르의 필수 요소 다섯 개가 모두 들어 있다.

| 시스템 | 구현 |
|---|---|
| 수동 획득 | 슬라임 때리기, 확률적으로 크리티컬(젤리 2배) |
| 타격감 | 스쿼시 + 파문 + 젤리 방울 + 피격 표정, 크리 시 금색 확대판 + 진동 |
| 자동 획득 | 젤리밭의 초당 수익 |
| 전투 | 서로 초당 피해를 주고받음. 쓰러지면 3층 물러나 기절 후 완전 회복 |
| 전투 연출 | 슬라임이 오른쪽으로 전진해 교전, 무기를 휘두르고 몬스터가 반격. 몬스터 20종 + 등급 수식어 |
| 업그레이드 | 손맛 · 행운 · 젤리밭 · 소화력 · 힘 훈련 · 체력 단련 (비용이 지수로 상승) |
| 일괄 구매 | ×1 / ×10 / 최대 토글 |
| 무기 | 6종, 20레벨마다 해금. 하나만 장착, 환생해도 유지 |
| 저장 / 오프라인 보상 | localStorage + 경과 시간 계산, 상한 8시간 |
| 환생(프레스티지) | 레벨 20 이상에서 영혼 획득. 레벨이 높을수록 더 많이 |
| 영혼 강화 | 영혼으로 사는 곱셈 강화 5종, 환생해도 유지 |

핵심 순환은 이렇게 닫힌다.

```
젤리 -> 먹이 -> 레벨 -> 공격력 상승 -> 사냥 가속 -> 젤리
```

## 코드 구조

파일 하나에 다 있고, 주석으로 열 개 구역이 나뉘어 있다. 핵심은 아래 네 층의 단방향 분리다.

- **상태(`state`)** — 저장되어야 하는 값만. 이게 세이브의 전부다.
- **파생 수치(`perClick`, `perSec` …)** — 상태에서 매번 계산하고 **절대 저장하지 않는다.** 저장하면 공식을 바꿀 때 옛 세이브가 틀린 값을 들고 있게 된다.
- **행동(`hit`, `feed`, `buy`, `rebirth`)** — 상태만 바꾸고 화면은 건드리지 않는다.
- **렌더(`render`)** — 상태를 화면에 비추기만 하고 상태를 바꾸지 않는다.

## 수치 설계

- **업그레이드 비용** = `기본가 × 성장률^보유수` (여러 단계는 [일괄 구매](#일괄-구매) 참고). 성장률 1.15는 쿠키클리커 이후의 사실상 표준값. 크게 잡으면 금방 벽에 막히고, 작게 잡으면 긴장감이 없어진다.
- **레벨업 요구 경험치** = `50 × 레벨^1.6`. 지수가 1보다 크므로 후반이 느려진다.
- **레벨 보상** = 레벨당 획득량 +5%, 곱셈으로 적용되어 클릭·자동 수익·공격력에 동시에 걸린다.
- **몬스터 체력** = `10 × 층^1.55`, **보상** = `8 × 층^1.25`. 체력의 지수가 보상의 지수보다 크므로 층이 오를수록 사냥이 느려지고, 그래서 힘 훈련에 투자할 이유가 생긴다. **이 두 지수의 차이가 전투 난이도 전체를 결정한다.**
- 기본 체력 10과 기본 공격력 2를 맞춰 **첫 몬스터를 5초에** 잡게 했다. 시작 직후 첫 보상이 몇 초 안에 들어오지 않으면 플레이어가 떠난다.
- **크리티컬** = 기본 5%에서 단계당 +4%, 상한 75%(18단계). 무기(+15%)와 영혼의 예리함(+5%)까지 더한 전체 상한은 95%. 손맛과 달리 기대값이 아니라 *분산*을 파는 업그레이드다. 0단계에서도 5%를 남겨 둔 것은, 한 번도 안 터지면 플레이어가 이 시스템의 존재를 모르기 때문이다. 상한을 100% 미만으로 막지 않으면 확률의 재미가 사라지고 손맛 업그레이드와 완전히 겹친다.

## 일괄 구매

업그레이드 목록 위의 `×1` `×10` `최대` 토글. 한 단계씩 수십 번 누르는 게 이 장르의 가장 큰 불편이라 넣었다.

k단계를 한꺼번에 사는 가격은 등비수열의 합이다.

```
base × g^n × (g^k − 1) / (g − 1)
```

`affordable`은 이 식을 k에 대해 뒤집어 로그로 한 번에 구한 뒤, 부동소수 오차를 실제 가격으로 보정한다. 젤리가 늘어날수록 반복문으로 세는 방식은 느려지지만 로그는 그렇지 않다.

설계에서 정한 것 두 가지.

- **모자라면 살 수 있는 만큼만 산다.** `×10`을 골랐는데 3단계치뿐이면 3단계를 사고 버튼에 `×3`이 뜬다. 모자란다고 버튼을 잠그면 초반 내내 `×10`이 죽은 버튼이 되어 애초의 불편이 그대로 남는다.
- **표시가와 청구액은 항상 같다.** 버튼에 뜬 숫자가 곧 빠져나가는 젤리다.

낱개로 10번 사는 것보다 `×10`이 아주 조금 비싸다. 낱개는 매 단계 `Math.floor`가 걸리고 일괄은 합계에 한 번만 걸리기 때문이다(10단계에 3젤리 수준). 단계당 1젤리 미만이고 가격은 지수로 커지므로 비율로는 계속 줄어든다.

`buyMode`는 `state`가 아니라 별도 변수다. 게임 진행이 아니라 화면 조작 상태라 세이브에 넣지 않았다 — 새로고침하면 `×1`로 돌아온다.

## 무기

스탯 바로 아래 `⚔️ 무기상점` 버튼으로 창이 열린다. 업그레이드와 다른 점은 **한 번만 사고, 하나만 장착한다**는 것.

| 무기 | 해금 | 가격 | 공격력 | 크리 |
|---|---|---|---|---|
| 🪵 나무 막대 | Lv.20 | 1K | +15 | +2% |
| 🪓 돌 도끼 | Lv.40 | 12K | +70 | +4% |
| 🗡️ 녹슨 단검 | Lv.60 | 150K | +320 | +6% |
| ⚔️ 강철 검 | Lv.80 | 2M | +1.5K | +8% |
| 🔥 화염 창 | Lv.100 | 30M | +7K | +11% |
| 🌙 영혼 낫 | Lv.120 | 500M | +35K | +15% |

공격력 보너스는 `힘 훈련`과 같은 자리에 더해지므로 레벨·영혼 배율을 그대로 받는다. 크리는 `행운`과 합산된다.

설계에서 중요한 세 가지.

- **가격이 성능보다 빨리 오른다.** 등급당 공격력 약 4.7배, 가격 약 15배. 그래서 다음 무기는 항상 한참 모아야 하는 목표로 남는다.
- **환생해도 사라지지 않는다.** 영혼과 같은 취급이다. 매 판 다시 사야 한다면 5억짜리 낫을 살 이유가 없고 상점 자체가 죽는다. `rebirth`에서 `weapons`/`equipped`를 따로 챙긴다.
- **크리 상한이 두 개다.** `CRIT_UP_CAP`(0.75)은 `행운`만으로 도달 가능한 선, `CRIT_CAP`(0.95)은 무기·영혼까지 더한 전체 상한. `행운 75% + 최고 무기 15% + 예리함 5% = 정확히 95%`가 되도록 맞췄다. 이게 어긋나면 마지막 무기나 영혼 강화가 "이미 상한이라 의미 없는" 물건이 된다.

무기를 추가하려면 `WEAPONS` 표에 행만 넣으면 된다. 효과 계산식(`weaponAtk`/`weaponCrit`)은 표를 그대로 읽으므로 손댈 필요가 없다 — 업그레이드와 다른 점이다.

## 영혼과 강화 창

스탯 아래 `🔧 강화` 버튼(무기상점 왼쪽)이 탭 두 개짜리 창을 연다. 왼쪽은 젤리로 사는 일반 업그레이드, 오른쪽은 영혼으로 사는 영구 강화다. **업그레이드가 모달로 들어가면서 사이드바를 없앴다** — 폰에서 강화 한 번 하려고 화면을 끝까지 내려야 했다.

보유 영혼은 머리말 오른쪽에 항상 떠 있다. 보석은 이모지가 아니라 `clip-path`로 깎은 도형이다. 이모지는 기기마다 그림이 달라서 같은 게임이 폰과 PC에서 다르게 보인다.

### 지급량은 레벨에 비례한다

```
영혼 = floor((레벨 / 20) ^ 1.5)
```

| 환생 레벨 | 20 | 40 | 60 | 100 | 200 | 400 |
|---|---|---|---|---|---|---|
| 영혼 | 1 | 2 | 5 | 11 | 31 | 89 |

예전 `sqrt(레벨/5)` 곡선은 레벨 20에 2개, 레벨 200에 6개였다. **더 키우고 환생할 이유가 사실상 없었다.** 지수를 1보다 크게 잡아야 "조금 더 버티면 훨씬 이득"이 성립한다.

### 보유량과 총합을 따로 센다

| 값 | 쓰임 |
|---|---|
| `souls` | 영혼 강화를 살 때 쓰는 잔고 |
| `soulsTotal` | 지금까지 얻은 총합. **전체 배율(`soulMult`)은 이쪽만 본다** |

**영혼을 써도 전체 배율은 줄지 않는다.** 하나로 합치면 "쓸까 말까"를 매번 저울질하게 되고, 그러면 대부분 안 쓰고 쌓아 둔다. 그러면 상점이 있으나 마나다.

### 영혼 강화 5종

| 이름 | 기본가 | 증가율 | 효과 |
|---|---|---|---|
| 영혼의 축복 | 1 | 1.6 | 모든 젤리 획득 +10%/단계 |
| 영혼의 검기 | 2 | 1.6 | 공격력 +15%/단계 |
| 영혼의 심장 | 2 | 1.6 | 최대 체력 +20%/단계 |
| 영혼의 지혜 | 3 | 1.7 | 먹이 경험치 +15%/단계 |
| 영혼의 예리함 | 4 | 1.8 | 크리티컬 +0.5%p/단계, 10단계 상한 |

일반 업그레이드가 덧셈이라면 이쪽은 곱셈이다. 판을 거듭할수록 효과가 커지는 게 프레스티지 층의 역할이다.

추가하려면 `SOUL_UPGRADES`에 행을 넣고 구역 3에 계산식을 하나 더 만들면 된다. 표만 넣으면 버튼과 가격까지만 생긴다 — 일반 업그레이드와 같은 규칙이다.

## 업그레이드 추가하기

두 곳을 고쳐야 한다. 표는 가격과 표시만 담당하고, 효과는 파생 수치에 있다.

1. `UPGRADES` 표에 행 추가 (`state.up`의 키는 자동 생성된다)

```js
{ id: 'friend', name: '친구 슬라임', base: 2000, growth: 1.30,
  desc: n => `초당 젤리 +${n * 5}` },
```

2. 효과를 계산식에 반영

```js
const perSec = () => (0.5 * state.up.field + 5 * state.up.friend) * levelMult() * soulMult();
```

상한을 두고 싶으면 표의 행에 `maxed`를 함께 넣는다. `render`가 이걸 보고 비용 자리에 `MAX`를 찍고 버튼을 잠근다(`행운`이 이 방식이다).

```js
{ id: 'friend', name: '친구 슬라임', base: 2000, growth: 1.30,
  desc:  n => `초당 젤리 +${n * 5}`,
  maxed: n => n >= 20 },
```

## 이펙트 다루기

`burst`가 클릭 한 번마다 DOM 노드를 만든다. 평타 6개, 크리 12개.

**노드는 반드시 스스로 지워져야 한다.** `animationend`에서 `remove()`를 부르는 게 그 장치다. 이걸 빼면 연타 1분에 수천 개가 쌓여 눈에 띄게 느려진다. 이펙트를 새로 추가할 때도 같은 규칙을 지킨다.

애니메이션은 `transform`과 `opacity`만 건드린다. `left`/`width` 같은 속성을 움직이면 매 프레임 레이아웃을 다시 계산해서 저사양 폰에서 끊긴다.

방울 개수·거리는 `burst` 안의 `n`과 `dist`로 조절한다. 저사양 기기를 노린다면 개수를 먼저 줄인다.

OS에 '동작 줄이기'가 켜져 있으면 `prefers-reduced-motion` 규칙이 모든 애니메이션을 0.01ms로 만든다. 이펙트는 사실상 안 보이지만 노드 정리는 그대로 동작한다.

## 전투 무대

슬라임은 왼쪽에서 오른쪽으로 전진해 몬스터와 붙는다. 레벨은 슬라임 머리 위, 몬스터 체력바는 몬스터 머리 위에 붙는다.

몬스터는 20종이고 21층부터는 같은 목록을 돌면서 `강화된` → `흉포한` → `심연의` → `전설의` 수식어가 붙는다. 등급마다 `.foe.t1`~`.t4`로 색이 다른 기운이 감돈다.

### 애니메이션이 서로 밟지 않게 하는 층 구조

`transform`은 요소당 하나만 살아남는다. 그래서 역할별로 요소를 나눴다.

| 요소 | 맡는 것 |
|---|---|
| `.mover` | 전진 (`translateX(var(--walk))`, 한 번만) |
| `.unit` | 반동 + 달려들기 + 반격에 밀리기 (`brawl`, 무한 반복) |
| `.sizer` | 레벨별 확대 (`render`가 인라인으로) |
| `.slime` | 피격 스쿼시 (`.squish`) + 레벨별 색조 |
| `.weap` | 무기 휘두르기 (`swing`) |
| `.ebody` | 몬스터 피격 + 반격 (`foeAct`) |

**`.slime`에 인라인 `transform`을 걸면 안 된다.** CSS 애니메이션이 인라인 스타일을 이기기 때문에, 예전처럼 `.slime`에 직접 확대를 걸면 애니메이션이 붙는 순간 크기가 날아간다. 그래서 `.sizer`를 따로 뒀다.

무기는 `.sizer` 안(슬라임과 같이 커진다)이면서 `.slime` 밖(레벨 색조를 안 받는다)에 있다. 색조를 `.sizer`에 걸면 무기 이모지까지 물든다.

네 애니메이션 모두 주기가 **1100ms로 같다.** 위상만 다르게 줘서 `휘두르기(52%) → 달려들기(55%) → 몬스터 피격(62%) → 몬스터 반격(88%) → 슬라임 밀림(90%)` 순서가 만들어진다. 주기가 어긋나면 때리는 동작과 맞는 동작이 따로 논다.

### 전진 거리는 실측한다

`--walk`를 고정 %로 두면 좁은 화면에서 슬라임이 몬스터를 덮는다. 화면 폭, 레벨에 따른 슬라임 크기, 체력바 폭이 전부 변수이기 때문이다. `layoutArena`가 이 셋을 재서 px로 넣는다.

```
멈춤 지점 = 몬스터 중심 − max(몸통 폭, 체력바 폭)/2 − 여유(24px)
```

`transform`은 `offsetLeft`/`offsetWidth`에 영향을 주지 않는다. 덕분에 전진 애니메이션을 끄지 않고도 '전진 전' 좌표를 그대로 읽을 수 있다. 호출은 최초 1회, `resize`, 그리고 레벨이 바뀔 때뿐이다 — 매 프레임 재면 레이아웃을 강제로 다시 계산하게 되어 느려진다.

체력바는 `position: absolute`로 띄웠다. 흐름에 두면 112px짜리 바가 `.foe`의 폭을 정해버려서 몬스터가 화면 안쪽으로 밀린다.

좁은 화면 보정은 **스타일시트 맨 끝의 `@media` 블록**에 모아 뒀다. 미디어쿼리도 특이도가 같으면 순서로 이기기 때문에, 위쪽에 두면 아래에 나오는 `.hpwrap` 기본 규칙에 밀려서 조용히 무시된다(실제로 한 번 당했다).

### 슬라임 체력과 죽음

슬라임도 초당 피해를 받는다. 체력이 0이 되면 **3층 물러나 2.5초 기절했다가 완전 회복하고 다시 붙는다.** 진행을 크게 되돌리는 벌이 아니라 속도 제한 장치다 — 방치형에서 진척이 날아가면 그 자리에서 게임을 접는다.

**생존 조건은 한 줄로 정리된다.**

```
초당 재생(최대체력 × 0.05) ≥ 초당 피해(0.35 × 층^1.05)  →  절대 안 죽는다
```

이 부등식이 "몇 층에서 막히는가"를 통째로 결정한다. 그 사이 구간에서는 `최대체력 ÷ (피해 − 재생)`초 동안 버티므로, 그 안에 몬스터를 잡으면 넘어간다.

| 상태 | 최대 체력 | 초당 재생 | 안전한 층 |
|---|---|---|---|
| Lv.1 맨몸 | 120 | 6 | 14층 |
| Lv.10 맨몸 | 174 | 8.7 | 21층 |
| Lv.30 맨몸 | 294 | 14.7 | 35층 |
| Lv.30 + 체력 단련 10 | 1,029 | 51.5 | 115층 |
| Lv.60 + 체력 단련 20 | 2,844 | 142 | 305층 |

처음 잡았던 값(`0.8 × 층^1.2`, 기본 체력 60)은 **3층부터 체력이 깎이고 30층에서 1.4초 만에 죽었다.** 벽이 너무 앞에 있으면 방치형이 성립하지 않는다.

기절 시간(`stunLeft`)은 저장하지 않는다. 연출용 상태라 새로고침하면 사라진다. 자리를 비운 동안의 체력 재생은 `load`에서 경과 시간만큼 한 번에 적용한다 — 20초만 비워도 가득 찬다.

### 연출과 게임 로직은 분리돼 있다

`fight()`의 피해 계산은 슬라임 위치와 무관하게 계속 돈다. 전진 애니메이션이 대미지를 막지 않는다는 뜻이다. 위치로 대미지를 막으면 층마다 이동 시간이 붙어서 `hpOfStage`/`rewardOfStage`로 맞춰 둔 진행 속도가 전부 어긋난다.

`renderArena`는 `state.stage`가 화면에 그려진 층과 다를 때만 몬스터를 갈아 끼운다. 공격력이 높으면 한 프레임에 수십 층을 넘기는데, 그때도 마지막 상태 한 번만 그리면 된다.

## 슬라임 표정

눈과 입은 `.slime` 안의 실제 요소다(`.eye.l` `.eye.r` `.mouth`). 의사요소로 두지 않은 이유는, 아플 때 눈 하나를 `>` 모양의 두 획으로 쪼개야 해서 눈마다 `::before`/`::after`가 따로 필요하기 때문이다. 두 획의 `transform-origin`을 꼭짓점에 두면 회전만으로 `><`가 만들어진다.

붉게 달아오르는 기운은 `filter`가 아니라 `.hurtglow` 레이어다. **`render()`가 매 프레임 `.slime`의 인라인 `filter`(레벨별 색조)를 덮어쓰기 때문에 클래스로 건 `filter`는 무조건 진다.**

표정 지속은 `hurtFace`의 260ms. 스쿼시(90ms)보다 길어야 표정이 읽힌다. 연타하면 `clearTimeout`으로 타이머가 계속 밀려서 때리는 내내 찡그린 얼굴이 유지된다.

## 세이브 다루기

**"고쳤는데 게임이 안 바뀐다"의 원인은 거의 항상 이전 세이브다.**

- 연습 중 초기화 — `F12` → Console에 `localStorage.clear(); location.reload();`
- 밸런스를 크게 뒤엎었을 때 — `SAVE_KEY`의 `v1`을 `v2`로 올린다. 기존 세이브가 무시된다.
- 후반 테스트 — Console에 `state.jelly = 1e9; state.level = 30;`

세이브는 브라우저별·도메인별이다. PC에서 키운 것을 폰에서 이어서 할 수는 없다. 그러려면 서버와 로그인이 필요하다.

## 배포

외부 리소스 참조가 0개인 자기완결 파일이라 어디에 올려도 그대로 동작한다.

- **GitHub Pages** — 무료, 영구 URL, `index.html`을 그대로 서비스하므로 사본이 생기지 않는다.
- **itch.io** — 실제 게임 유통 플랫폼. 방치형을 찾아서 노는 사용자가 모여 있다.
- **Netlify Drop / Cloudflare Pages** — 폴더를 드래그&드롭하면 즉시 URL이 나온다.

배포하면 소스가 100% 공개되고 콘솔로 치트가 가능하다. 싱글플레이라 문제되지 않지만, 랭킹을 넣는다면 서버 검증이 필요해진다.
